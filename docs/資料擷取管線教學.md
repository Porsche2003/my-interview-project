## 1. 整體架構一覽

```
                    npm run ingest
                          │
                          ▼
              ┌───────────────────────┐
              │       run.ts           │  主流程：呼叫兩個 fetcher → 合併 → 寫入 → 記錄結果
              └───────────────────────┘
                    │             │
       ┌────────────┘             └────────────┐
       ▼                                        ▼
┌─────────────────┐                    ┌─────────────────┐
│  fetch-twse.ts    │                    │  fetch-tpex.ts    │
│  上市（TWSE）      │                    │  上櫃（TPEx）      │
└─────────────────┘                    └─────────────────┘
       │  用到                                  │  用到
       ├─▶ http.ts       （重試 + User-Agent）  ├─▶ http.ts
       ├─▶ roc-date.ts   （民國年→西元）        ├─▶ roc-date.ts
       └─▶ types.ts      （zod 驗證 + numOrNull） └─▶ types.ts
                          │
                          ▼（兩邊合併成 NormalizedQuote[]）
                  ┌───────────────────┐
                  │     upsert.ts       │  分批 upsert 進 Supabase
                  └───────────────────┘
                          │  用到
                          ▼
                ┌───────────────────────┐
                │  supabase-admin.ts      │  用 service_role 金鑰建立的 admin client
                └───────────────────────┘
                          │
                          ▼
              Supabase：stocks + daily_quotes 兩張表
```

**核心設計原則**（對應教學文件第 10 章）：

- **抓取與寫入分兩階段**：先把兩個市場的資料都抓進記憶體、驗證好，再一次寫入資料庫。任何一步驗證失敗，都不會寫入半殘的資料。
- **兩個市場互相獨立**：`run.ts` 用 `Promise.allSettled`，就算 TPEx 那天掛掉，TWSE 的資料還是能正常寫入。
- **冪等**：靠 `daily_quotes` 的複合主鍵 `(stock_id, trade_date)` + `upsert`，同一天重跑多次，結果都一樣，不會產生重複資料。
- **密鑰隔離**：`service_role` 金鑰只存在於 `supabase-admin.ts`，這支腳本**不會**被 Next.js app 打包進瀏覽器（它甚至不在 `src/` 底下）。

## 2. 檔案逐一說明

| 檔案 | 職責 | 為什麼獨立成一個檔案 |
|---|---|---|
| [scripts/ingest/roc-date.ts](../scripts/ingest/roc-date.ts) | 把證交所回傳的民國年日期字串（如 `"1150701"`）轉成西元 ISO 格式（`"2026-07-01"`） | 這個轉換邏輯兩個市場都會用到，且容易寫錯（民國年+1911 這個魔術數字），獨立出來才好單獨測試 |
| [scripts/ingest/types.ts](../scripts/ingest/types.ts) | 用 **Zod** 定義四支來源 API 的原始格式（形狀驗證），以及正規化後要寫入資料庫的統一格式 `NormalizedQuote` | 把「驗證外部資料長什麼樣子」和「轉換成我們要的格式」分開，是關注點分離；也是防止證交所改欄位時程式默默壞掉的第一道防線 |
| [scripts/ingest/http.ts](../scripts/ingest/http.ts) | 帶重試機制（指數退避）與正確 `User-Agent` 的 `fetch` 包裝 | 兩個市場都要打外部 API，重試邏輯只寫一次、共用 |
| [scripts/ingest/fetch-twse.ts](../scripts/ingest/fetch-twse.ts) | 抓 TWSE 的兩支 API（收盤價/成交量 + 本益比），驗證後依代號合併成 `NormalizedQuote[]` | 上市市場的抓取邏輯 |
| [scripts/ingest/fetch-tpex.ts](../scripts/ingest/fetch-tpex.ts) | 同上，但抓 TPEx 的兩支 API | 上櫃市場的抓取邏輯。和 TWSE 那支結構很像但**欄位名稱完全不同**，所以沒有硬拆共用函式，保留清楚可讀 |
| [scripts/ingest/supabase-admin.ts](../scripts/ingest/supabase-admin.ts) | 用 `SUPABASE_SERVICE_ROLE_KEY` 建立一個繞過 RLS 的 Supabase client | 這個 client **只能**被這個獨立腳本使用，故意不放進 `src/utils/supabase/`，避免哪天被 import 進 Next.js app |
| [scripts/ingest/upsert.ts](../scripts/ingest/upsert.ts) | 把 `NormalizedQuote[]` 分批 upsert 進 `stocks` 和 `daily_quotes` 兩張表 | 寫入邏輯集中一處，之後要改寫入策略（例如加交易 transaction）只需要改這裡 |
| [scripts/ingest/run.ts](../scripts/ingest/run.ts) | 主流程：呼叫兩個 fetcher → 合併結果 → 呼叫 upsert → 印出統計 → 決定結束碼 | 這是 `npm run ingest` 實際執行的進入點 |

**依賴方向**（誰 import 誰）：`run.ts` → `fetch-twse.ts` / `fetch-tpex.ts` / `upsert.ts` → `http.ts` / `roc-date.ts` / `types.ts` / `supabase-admin.ts`。越底層的檔案越不知道「股票」這個業務概念（`http.ts` 只管重試、`roc-date.ts` 只管日期轉換），這樣它們才好被將來的其他資料源重複使用（見第 7 節）。

## 3. 資料來源：TWSE / TPEx API 細節

這四支 API 都是公開的、不需要金鑰，但欄位名稱、日期格式都是實測確認出來的（不是憑印象猜的），之後如果程式壞了，可以回來對照這張表。

| 市場 | 用途 | URL | 關鍵欄位 |
|---|---|---|---|
| 上市 TWSE | 收盤價/成交量 | `https://openapi.twse.com.tw/v1/exchangeReport/STOCK_DAY_ALL` | `Date`, `Code`, `Name`, `ClosingPrice`, `TradeVolume` |
| 上市 TWSE | 本益比 | `https://openapi.twse.com.tw/v1/exchangeReport/BWIBBU_ALL` | `Date`, `Code`, `PEratio` |
| 上櫃 TPEx | 收盤價/成交量 | `https://www.tpex.org.tw/openapi/v1/tpex_mainboard_quotes` | `Date`, `SecuritiesCompanyCode`, `CompanyName`, `Close`, `TradingShares` |
| 上櫃 TPEx | 本益比 | `https://www.tpex.org.tw/openapi/v1/tpex_mainboard_peratio_analysis` | `Date`, `SecuritiesCompanyCode`, `PriceEarningRatio` |

**三個容易踩雷、我們已經處理掉的細節**：

1. **日期是民國年**：`"1150701"` 代表民國115年07月01日（西元 2026-07-01）。四支 API 都是這個格式。→ 由 `roc-date.ts` 統一轉換。
2. **TPEx 會擋掉沒有瀏覽器特徵的請求**（回 403）：我們的自動化網頁擷取工具實測被擋，但帶正常的 `User-Agent` header 就正常。→ 已寫死在 `http.ts` 的 `fetchJsonWithRetry` 裡。
3. **有些股票沒有本益比**：主要是 ETF（例如 `00400A`），因為 ETF 不適用本益比概念，兩邊 API 對這種標的的 `PEratio`/`PriceEarningRatio` 欄位會回傳空字串 `""`。→ 由 `types.ts` 的 `numOrNull()` 統一轉成 `null`，不會讓程式崩潰或誤把空字串當數字寫入。

> **注意**：`STOCK_DAY_ALL` 這支 API 回傳的清單**包含 ETF**，不是純粹的個股清單。目前的程式沒有過濾掉它們（連 ETF 的股價一起存，本益比欄位是 `null`）。如果之後想要「股票資訊站」只顯示真正的個股，需要額外加過濾邏輯——這是一個**尚未做的決定**，不是 bug。

## 4. 如何本機執行

**先決條件**：`.env.local` 裡要有三個環境變數：

```
NEXT_PUBLIC_SUPABASE_URL=...
NEXT_PUBLIC_SUPABASE_ANON_KEY=...
SUPABASE_SERVICE_ROLE_KEY=...      ← 從 Supabase Dashboard → Settings → API 取得
```

`SUPABASE_SERVICE_ROLE_KEY` 這把鑰匙**繞過所有 RLS**，等同資料庫最高權限：
- 絕對不能加 `NEXT_PUBLIC_` 前綴（一加，就會被打包進瀏覽器，任何訪客都看得到）。
- `.env.local` 已被 `.gitignore` 排除，不會進 git，維持這個狀態。

**執行**：

```bash
npm run ingest
```

這個指令實際上是：

```
node --env-file=.env.local --import tsx scripts/ingest/run.ts
```

- `--env-file=.env.local`：Node 20.6+ 內建功能，直接讀 `.env.local`，不需要額外裝 `dotenv` 套件。
- `--import tsx`：讓 Node 能直接執行 `.ts` 檔，不用先編譯成 `.js`。

**正常輸出長這樣**：

```
[ingest] 開始擷取 TWSE / TPEx 資料...
[ingest] TWSE 上市：1368 筆
[ingest] TPEx 上櫃：1012 筆
[ingest] 完成，共寫入 2380 筆，耗時 2.9s
```

## 5. 我們怎麼測試（可重複當健康檢查用）

實作完成後，我們做了四項驗證，之後改動這條管線都應該重跑這四項：

### ① 資料真的寫進去了

用 anon key 查 PostgREST 的 `Content-Range` header 拿總筆數（因為 RLS 允許公開讀取）：

```bash
source .env.local
curl -s "${NEXT_PUBLIC_SUPABASE_URL}/rest/v1/daily_quotes?select=stock_id&limit=1" \
  -H "apikey: ${NEXT_PUBLIC_SUPABASE_ANON_KEY}" \
  -H "Prefer: count=exact" -H "Range: 0-0" -D - -o /dev/null | grep -i "content-range"
```

### ② 抽查一筆熟悉的資料是否合理

例如查台積電（2330），肉眼確認股價、本益比數字有沒有離譜：

```bash
curl -s "${NEXT_PUBLIC_SUPABASE_URL}/rest/v1/daily_quotes?stock_id=eq.2330&select=*" \
  -H "apikey: ${NEXT_PUBLIC_SUPABASE_ANON_KEY}"
```

### ③ 冪等性：重跑不會產生重複資料

```bash
npm run ingest   # 再跑一次
# 再用①的指令查一次筆數，應該和第一次跑完全一樣
```

### ④ RLS 真的擋住前端寫入

故意用 **anon key**（不是 service_role）嘗試寫入，預期收到 `401` + RLS 違規訊息：

```bash
echo '{"id":"9999","name":"test","market":"TWSE"}' > /tmp/test.json
curl -s -w "\nHTTP: %{http_code}\n" -X POST "${NEXT_PUBLIC_SUPABASE_URL}/rest/v1/stocks" \
  -H "apikey: ${NEXT_PUBLIC_SUPABASE_ANON_KEY}" \
  -H "Authorization: Bearer ${NEXT_PUBLIC_SUPABASE_ANON_KEY}" \
  -H "Content-Type: application/json" --data @/tmp/test.json
# 預期：{"code":"42501", "message":"new row violates row-level security policy..."}  HTTP: 401
```

> 這四項也是你面試被問「你怎麼知道這條管線是對的」時最好的答案——不是「我跑了看畫面正常」，而是「我驗證了寫入正確性、冪等性、和安全邊界」。

## 6. 如何添加欄位（實戰演練）

假設你想加一個新欄位：**漲跌幅（`change`）**。兩邊 API 都有這個資料（TWSE 叫 `Change`，TPEx 也叫 `Change`）。步驟固定是這四步，順序不能顛倒：

### Step 1：資料庫先加欄位（migration）

```bash
npx supabase migration new add_change_to_daily_quotes
```

寫入新產生的 `.sql` 檔：

```sql
alter table public.daily_quotes
  add column change numeric(10, 2);
```

推上雲端：

```bash
npx supabase db push
```

> 為什麼先動資料庫？因為 [types.ts](../scripts/ingest/types.ts) 之後會需要一個地方讓新欄位「存在」，資料庫是所有下游的依歸。

### Step 2：`types.ts` 加進 Zod schema 與 `NormalizedQuote`

```ts
// TwseQuoteRowSchema 加一行
export const TwseQuoteRowSchema = z.object({
  Date: z.string(),
  Code: z.string(),
  Name: z.string(),
  ClosingPrice: z.string(),
  TradeVolume: z.string(),
  Change: z.string(),        // ★ 新增
})

// NormalizedQuote 加一個欄位
export type NormalizedQuote = {
  // ...原本的欄位
  change: number | null       // ★ 新增
}
```

TPEx 的 `TpexQuoteRowSchema` 同樣加 `Change: z.string()`。

### Step 3：`fetch-twse.ts` / `fetch-tpex.ts` 補上映射

```ts
return quotes.map((q) => ({
  // ...原本的欄位
  change: numOrNull(q.Change),   // ★ 新增
}))
```

兩個檔案都要改（因為兩個市場都要抓這個欄位）。

### Step 4：`upsert.ts` 補上寫入映射

```ts
const quoteRows = quotes.map((q) => ({
  // ...原本的欄位
  change: q.change,   // ★ 新增
}))
```

### Step 5：驗證

```bash
npx tsc --noEmit     # 型別檢查——如果 NormalizedQuote 加了必填欄位，這裡會抓到哪裡漏改
npm run ingest       # 實際跑一次
# 用第 5 節的方法①②確認新欄位有值
```

**這個順序背後的心法**：資料庫 schema 是「真相來源」，`types.ts` 是「型別契約」，兩個 `fetch-*.ts` 是「契約的實作」，`upsert.ts` 是「契約的出口」。每一層都会靠 TypeScript 的型別檢查逼你把下一層改完——這就是為什麼第 5 步先跑 `tsc --noEmit` 很重要，它會在你忘記改某個檔案時直接報錯，而不是等到真正寫入資料庫才發現欄位是 `undefined`。

## 7. 如何新增更多資料來源（實戰演練）

假設你想加「**三大法人買賣超**」這個新資料（證交所也有對應的 Open API）。這比第 6 節複雜，因為它很可能是一張**新表**，而不是加欄位。判斷方式：

> **加欄位**：新資料和現有的「一檔股票、一個交易日」是一對一關係（例如漲跌幅）。
> **開新表**：新資料有自己的維度、或者不是每天每檔都有（例如三大法人買賣超通常也是「一檔一天一筆」，但語意上是不同的資料集，開新表更清楚；若是像「財報」這種「一檔一季一筆」，維度不同，**必須**開新表）。

以「三大法人買賣超」（假設它和 `daily_quotes` 一樣是「一檔一天一筆」，但選擇開新表以保持語意清楚）為例，完整步驟：

### Step 1：確認 API 格式（不要用猜的）

用 `curl` 直接打一次，看實際欄位名稱：

```bash
curl -s -A "Mozilla/5.0" "https://openapi.twse.com.tw/v1/fund/T86" | head -c 500
```

記下欄位名稱、日期格式（大機率還是民國年）、數值欄位有沒有空字串的情況。

### Step 2：Migration 開新表

```bash
npx supabase migration new add_institutional_trading
```

```sql
create table public.institutional_trading (
  stock_id text not null references public.stocks(id) on delete cascade,
  trade_date date not null,
  foreign_buy_sell bigint,     -- 外資買賣超
  trust_buy_sell bigint,        -- 投信買賣超
  dealer_buy_sell bigint,       -- 自營商買賣超
  primary key (stock_id, trade_date)   -- 一樣用複合主鍵保證冪等
);

alter table public.institutional_trading enable row level security;

create policy "Institutional trading is viewable by everyone."
  on public.institutional_trading for select using (true);
-- 一樣不給 insert/update/delete 政策，只有 service_role 能寫
```

### Step 3：在 `types.ts` 定義新的 schema

```ts
export const TwseInstitutionalRowSchema = z.object({
  Date: z.string(),
  Code: z.string(),
  ForeignInvestorsExcludingDealers: z.string(),
  InvestmentTrust: z.string(),
  Dealers: z.string(),
})

export type NormalizedInstitutionalTrading = {
  stockId: string
  tradeDate: string
  foreignBuySell: number | null
  trustBuySell: number | null
  dealerBuySell: number | null
}
```

### Step 4：新增 `fetch-twse-institutional.ts`

**重用**已經寫好的 `http.ts`（重試邏輯）和 `roc-date.ts`（日期轉換）——這就是第 2 節提到「越底層的檔案越不涉及業務概念」的好處，完全不用重寫：

```ts
import { z } from 'zod'
import { fetchJsonWithRetry } from './http'
import { rocDateToIso } from './roc-date'
import { TwseInstitutionalRowSchema, numOrNull, type NormalizedInstitutionalTrading } from './types'

const URL = 'https://openapi.twse.com.tw/v1/fund/T86'

export async function fetchTwseInstitutionalTrading(): Promise<NormalizedInstitutionalTrading[]> {
  const raw = await fetchJsonWithRetry(URL)
  const rows = z.array(TwseInstitutionalRowSchema).parse(raw)

  return rows.map((r) => ({
    stockId: r.Code,
    tradeDate: rocDateToIso(r.Date),
    foreignBuySell: numOrNull(r.ForeignInvestorsExcludingDealers),
    trustBuySell: numOrNull(r.InvestmentTrust),
    dealerBuySell: numOrNull(r.Dealers),
  }))
}
```

### Step 5：新增對應的 upsert 函式

在 `upsert.ts` 加一個新函式（不要塞進現有的 `upsertQuotes`，職責分開）：

```ts
export async function upsertInstitutionalTrading(
  rows: NormalizedInstitutionalTrading[]
): Promise<void> {
  const dbRows = rows.map((r) => ({
    stock_id: r.stockId,
    trade_date: r.tradeDate,
    foreign_buy_sell: r.foreignBuySell,
    trust_buy_sell: r.trustBuySell,
    dealer_buy_sell: r.dealerBuySell,
  }))

  for (const batch of chunk(dbRows, BATCH_SIZE)) {
    const { error } = await supabaseAdmin
      .from('institutional_trading')
      .upsert(batch, { onConflict: 'stock_id,trade_date' })
    if (error) throw new Error(`upsert institutional_trading 失敗: ${error.message}`)
  }
}
```

### Step 6：在 `run.ts` 加一條 `Promise.allSettled` 分支

```ts
const [twseResult, tpexResult, institutionalResult] = await Promise.allSettled([
  fetchTwseQuotes(),
  fetchTpexQuotes(),
  fetchTwseInstitutionalTrading(),   // ★ 新增
])

// ...原本的處理邏輯之後，加：
if (institutionalResult.status === 'fulfilled') {
  await upsertInstitutionalTrading(institutionalResult.value)
  console.log(`[ingest] 三大法人：${institutionalResult.value.length} 筆`)
} else {
  hasFailure = true
  console.error('[ingest] 三大法人擷取失敗:', institutionalResult.reason)
}
```

**這個模式可以無限套用到任何新資料源**：只要新資料「跟股票有關、需要 API 抓」，就是這六步——確認格式 → migration → schema → fetcher → upsert 函式 → 掛進 `run.ts`。`Promise.allSettled` 保證資料源之間互不拖累，加第五個、第六個資料源時，前面四個都不會因為新的失敗而連帶壞掉。

## 8. 常見錯誤排除

| 錯誤訊息 | 原因 | 解法 |
|---|---|---|
| `Missing NEXT_PUBLIC_SUPABASE_URL or SUPABASE_SERVICE_ROLE_KEY` | `.env.local` 沒有這兩個變數，或執行時沒加 `--env-file` | 確認 `.env.local` 內容；一定要用 `npm run ingest`（已內建 `--env-file`），不要直接 `npx tsx scripts/ingest/run.ts` |
| `HTTP 403 Forbidden`（來自 TPEx） | TPEx 擋掉沒有瀏覽器特徵的請求 | 確認 `http.ts` 裡的 `User-Agent` header 沒被移除 |
| `ZodError: ... Expected string, received undefined` | 來源 API 改了欄位名稱或格式 | 用 `curl` 直接打一次那支 API，對照 `types.ts` 裡的 schema，更新欄位名稱 |
| `upsert daily_quotes 失敗: new row violates row-level security policy` | 誤用了 anon key 而非 service_role key | 檢查 `supabase-admin.ts` 讀到的是 `SUPABASE_SERVICE_ROLE_KEY` 而非 `NEXT_PUBLIC_SUPABASE_ANON_KEY` |
| `Top-level await is currently not supported with the "cjs" output format` | 在 `.ts` 檔案最外層直接寫 `await`，但專案沒有設定 `"type": "module"` | 把邏輯包進 `async function main() { ... } \n main()`，不要用 top-level await |
| 筆數比預期少很多 | 可能剛好在證交所非交易日（假日/國定假日）執行 | 正常現象；改在下一個交易日重跑即可看到完整資料 |
