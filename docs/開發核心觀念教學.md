## 第 0 章：先建立「大圖像」（最重要，別跳過）

在懂任何單一觀念之前，你要先有一張「一個請求發生了什麼事」的地圖。整個系統有**三個世界**，它們能做的事、能不能被信任，完全不同：

```
┌──────────────┐   HTTPS 請求    ┌───────────────────────┐   SQL / HTTPS   ┌──────────────────────┐
│  使用者瀏覽器   │ ─────────────▶ │   Next.js (跑在 Vercel) │ ──────────────▶ │  Supabase             │
│  (Client 世界) │ ◀───────────── │   (Server 世界)         │ ◀────────────── │  Postgres + Auth      │
└──────────────┘   HTML / JSON   │                        │                 └──────────────────────┘
                                  └───────────────────────┘                            ▲
   ↑                                                                                   │ 排程寫入（每天收盤後）
   │ 使用者看得到、改得到這裡的一切                                            ┌──────────────────────┐
   │ → 不可信任                                                              │  擷取程式 (Cron Job)   │
                                                                            │  抓 證交所 API → 寫入   │
                                                                            └──────────────────────┘
```

| 世界 | 在哪裡執行 | 誰控制它 | 能不能信任？ | 能放密鑰嗎？ |
|---|---|---|---|---|
| **Client（瀏覽器）** | 使用者的電腦/手機 | **使用者** | ❌ 完全不可信 | ❌ 絕對不行 |
| **Server（Next.js）** | Vercel 的機器 | **你** | ✅ 可信 | ✅ 可以 |
| **Database（Supabase）** | Supabase 的機器 | **你** | ✅ 可信 | ✅ 可以 |

> **這張表是後面所有安全觀念的根**。「使用者控制的東西不可信」這句話，會解釋 getUser vs getSession、RLS、Server/Client 拆分——全部。先把它刻進腦袋。

你的網站還有一條**離線的資料流**（圖右下）：證交所的資料不是使用者來訪時才抓，而是**背景排程**抓好、寫進 Supabase，使用者來的時候只是讀資料庫。這條流就是第 10 章的主題。

## 第 1 章：Server / Client 元件拆分

> **一句話**：Next.js 的畫面預設在「Server 世界」算好，只有需要互動的零件才送去「Client 世界」。搞懂這條界線，才看得懂後面所有安全問題。

### 從零開始：問題是什麼？

傳統的 React（純前端）是這樣：伺服器丟一包幾乎空白的 HTML + 一大包 JavaScript 給瀏覽器，**所有畫面都在使用者的瀏覽器裡用 JS 組出來**。問題：
- 要抓資料庫，得先讓瀏覽器打 API，多一趟來回、慢。
- 資料庫密碼、API key 不可能放進去（會被使用者看光，見上面那張表）。
- JS 包很大，手機載入慢。

Next.js 的 App Router 改變了這件事：**畫面預設在伺服器上算好**（Server Component），算好的結果（HTML）直接送到瀏覽器。只有「需要互動」的零件（按鈕點擊、輸入框、用 `useState`）才標記成 Client Component，送去瀏覽器執行。

### 它怎麼運作

- **Server Component（預設）**：檔案裡**不寫** `'use client'`。可以直接 `await` 資料庫、可以讀環境變數密鑰、不會把這段程式的 JS 送給瀏覽器。
- **Client Component**：檔案**第一行寫** `'use client'`。可以用 `useState`、`onClick`、`useEffect`、`window`、`localStorage`。

```tsx
// app/page.tsx —— Server Component（預設，沒有 'use client'）
import { getStockDetail } from '@/services/stocks'   // 直接查資料庫

export default async function Page() {
  const stock = await getStockDetail('2330')   // ✅ 在伺服器上跑，安全
  return (
    <div>
      <h1>{stock.name}</h1>
      <FavoriteButton stockId={stock.id} />     {/* 互動零件交給 Client */}
    </div>
  )
}
```

```tsx
// app/ui/favorite-button.tsx —— Client Component
'use client'
import { useState } from 'react'

export default function FavoriteButton({ stockId }: { stockId: string }) {
  const [faved, setFaved] = useState(false)   // ✅ 互動只能在 Client
  return <button onClick={() => setFaved(!faved)}>{faved ? '★' : '☆'}</button>
}
```

**關鍵心法**：盡量讓元件留在 Server（預設），只有真的需要互動的「葉子」才加 `'use client'`。`'use client'` 是一條**邊界線**——一旦某檔案標了它，它 import 的東西也會一起被打包進瀏覽器。

### 對應到你的專案

這就是為什麼你的 Supabase client 有**兩個版本**：

- [src/utils/supabase/server.ts](../src/utils/supabase/server.ts) —— 給 Server 世界用，從 `cookies()` 讀登入狀態。
- [src/utils/supabase/client.ts](../src/utils/supabase/client.ts) —— 給 Client 世界（瀏覽器）用，`createBrowserClient`。

它們不是重複，是**因為跑在兩個不同世界，連線方式不一樣**。你 [src/app/page.tsx](../src/app/page.tsx) 是 Server Component，所以能直接 `await getMyProfile()`。

### 深入 & 面試講法

- **密鑰保護機制（要記）**：Next.js 只有 `NEXT_PUBLIC_` 開頭的環境變數會送進瀏覽器；沒這前綴的，在 Client 端會被替換成空字串。所以 `SUPABASE_SERVICE_ROLE_KEY`（萬能金鑰）這種東西**絕不能**加 `NEXT_PUBLIC_`，它就只會待在 Server 世界。
- 想更保險，可在純伺服器檔案頂端 `import 'server-only'`，這樣一旦有人不小心把它 import 進 Client，**建置時就會報錯**。
- **面試講法**：「我用 Server Components 在伺服器端直接存取資料來源，減少瀏覽器的往返與 JS bundle，敏感金鑰只存在於 Server 世界；只有需要互動的元件才用 `'use client'` 標記成 Client Component，把界線縮到最小。」

## 第 2 章：`getSession()` vs `getUser()` —— 信任問題

> **一句話**：`getSession()` 是「讀使用者自己交出來的紙條」，`getUser()` 是「打電話跟發證機關確認這張紙條真偽」。在 Server 端保護資料，**只能信 `getUser()`**。

### 從零開始：問題是什麼？

回到第 0 章那張表：**瀏覽器（Client）是使用者控制的，不可信**。登入後，使用者的身分證明（一個叫 JWT 的 token）存在瀏覽器的 cookie 裡。每次請求，瀏覽器把這張 cookie 一起送上來。

問題來了：這張 cookie 是從「不可信的世界」送來的。你怎麼知道它**沒被竄改、沒過期、是真的**？

### 它怎麼運作

JWT（JSON Web Token）長這樣，三段用點隔開：`header.payload.signature`
- `payload` 裡有「我是 user 123」這種資訊——**任何人都能解開來讀，甚至偽造一份說自己是 user 999**。
- `signature` 是用「只有 Auth 伺服器知道的密鑰」簽出來的封印，用來證明這張 token 沒被改過。

兩個方法的差別：

| | `getSession()` | `getUser()` |
|---|---|---|
| 做什麼 | 從 cookie 把 token **讀出來、本地解碼** | 把 token **送回 Supabase Auth 伺服器驗證** |
| 有沒有網路往返 | ❌ 沒有（純本地） | ✅ 有（每次都問發證機關） |
| 速度 | 快 | 慢一點點 |
| 能不能信任 | ❌ 在 Server 端**不可信** | ✅ 可信 |
| 比喻 | 看一眼對方自己掏出的識別證 | 打電話回發證單位查證這張證 |

Supabase 官方原話：**永遠用 `getUser()` 保護頁面與資料；絕不要在伺服器程式（如 middleware）裡信任 `getSession()`，它不保證會重新驗證 token。`getUser()` 安全，因為它每次都向 Auth 伺服器重新驗證。**

### 對應到你的專案

你已經做對了，而且註解都寫了——這是加分項，別改壞：

- [src/middleware.ts:25](../src/middleware.ts) → `const { data: { user } } = await supabase.auth.getUser()`，註解寫著「安全核心：務必使用 getUser() 而非 getSession()」。✅
- [src/services/profile.ts:8](../src/services/profile.ts) → 查資料前先 `getUser()` 驗身分。✅

### 深入 & 面試講法

- **效能取捨**：`getUser()` 每次有網路往返，比較慢。所以業界常見作法是**雙層**：在最外層（攔截器）用便宜的方式做「樂觀檢查」快速擋掉明顯沒登入的人；真正碰到敏感資料時，在靠近資料的那層用 `getUser()` 做「安全檢查」。這正好接到第 3、4 章。
- **面試講法**：「`getSession()` 只從 cookie 本地解碼，而 cookie 屬於用戶端可控範圍，無法作為伺服器端的信任依據；`getUser()` 會向 Auth 伺服器重新驗證 JWT 簽章與有效性，所以所有受保護資源我都以 `getUser()` 為準。」

> ⚠️ **Next.js 16 命名變動**：Next 16 把「每個請求都會先經過的攔截層」的慣例檔名改成 **`proxy.ts`（Proxy）**，舊的 `middleware.ts`（Middleware）主要保留給 Edge runtime 的情境。你現在用的是 [src/middleware.ts](../src/middleware.ts)，**功能正確**，但等我們實作登入時，會去對齊這版官方最新慣例（屆時我會先讀 `node_modules/next/dist/docs/` 確認）。觀念不變：這一層只做「樂觀檢查」，不要在這裡查資料庫。

## 第 3 章：RLS 是「最後一道防線」，不是唯一防線

> **一句話**：RLS 是直接長在資料庫上的權限規則——就算前面所有程式都被繞過，它仍能擋住「A 偷看 B 的資料」。但它**不該**拿來寫複雜商業邏輯。

### 從零開始：問題是什麼？

想像資料庫是一間銀行金庫。你的 Next.js 後端是櫃員，平常大家都透過櫃員辦事。但 Supabase 有個特性：**前端有時可以直接用瀏覽器的 SDK 連資料庫**（跳過你的後端櫃員）。那如果有人不透過櫃員、直接想搬走別人的存款怎麼辦？

RLS（Row Level Security，行級安全）就是**裝在金庫每一個抽屜上的鎖**：規則寫在資料庫層，無論你從哪條路來，都得通過。

### 它怎麼運作

RLS 是一條條 SQL 規則，綁在「資料表 + 操作（select/insert/update/delete）」上。資料庫執行查詢時，會自動幫你加上條件。

看你 [supabase/migrations/20260620144945_init_schema.sql](../supabase/migrations/20260620144945_init_schema.sql) 的例子：

```sql
alter table public.profiles enable row level security;   -- 開鎖總開關

-- 規則1：所有人都能「讀」任何人的 profile
create policy "Public profiles are viewable by everyone."
  on public.profiles for select using (true);

-- 規則2：只能「改」自己的 profile（auth.uid() 是當前登入者的 id）
create policy "Users can update their own profile."
  on public.profiles for update using (auth.uid() = id);
```

第二條的意思是：當有人發出 `update profiles ...`，資料庫**自動**附加 `where auth.uid() = id`。所以就算駭客想改別人的資料，資料庫層直接擋掉。

### 對應到你的專案 & 將來的股票表

你的 `profiles` 表已經有 RLS。將來的股票表（第 10 章）會用到一個常見模式——**公開讀、禁止前端寫**：

```sql
-- 股價是公開資訊，誰都能讀
create policy "Quotes are public." on public.daily_quotes for select using (true);
-- 但沒有任何 insert/update 政策 → 前端一律不能寫，只有後端用 service_role 金鑰能寫
```

### 深入 & 面試講法（這題很會考）

**為什麼不把所有商業邏輯都塞進 RLS / Trigger？** 因為 RLS 的缺點是：
1. **難測試、難除錯**：邏輯藏在 SQL 政策裡，沒有好用的單元測試與斷點。
2. **叫不動外部世界**：RLS 裡很難打第三方 API（寄 LINE 通知、串金流 webhook）。
3. **複雜 SQL 吃資料庫 CPU**：把多層交叉權限全用 SQL 算，資料庫會變成瓶頸。

所以業界的分工是：

> **RLS 負責「資料不外洩」這條死線（防越權）；動態的、會呼叫外部、需要被測試的商業邏輯，放在 Next.js 的 Server 層（第 4 章的 DAL）。**

- **面試完美回答**：「RLS 是我的最後一道防線，確保即使應用層出包，使用者也無法越權存取他人資料。但我不會把商業邏輯塞進 RLS——它難以單元測試、無法呼叫外部 API、複雜 SQL 也會消耗資料庫 CPU。因此我把『權限防禦』交給 RLS，把『動態商業邏輯』留在 Server 層。這叫**縱深防禦（defense in depth）**：多層各司其職，不依賴單點。」

## 第 4 章：DAL —— 資料存取層（Data Access Layer）

> **一句話**：把「所有碰資料庫的程式」集中關進一個資料夾，畫面與路由只透過它拿資料，不直接碰 SQL。

### 從零開始：問題是什麼？

新手寫法是哪裡要資料、就在哪裡直接 `supabase.from('stocks').select('*')...`。畫面元件、API、各個頁面到處都是這種查詢。問題：
- 同一張表的查詢散落十幾個地方，改一次欄位要改十幾處。
- 沒辦法寫測試（邏輯黏在畫面裡）。
- 安全檢查（getUser）很容易**漏寫**某一處。

DAL 的概念：**蓋一道專門的窗口**，所有要資料的人都來這個窗口拿，窗口內部統一處理「驗身分 → 查資料 → 只回傳該回傳的欄位」。

### 對應到你的專案

你已經有雛形了：[src/services/profile.ts](../src/services/profile.ts) 就是 DAL。

```ts
export async function getMyProfile() {
  const supabase = await createClient()
  const { data: { user } } = await supabase.auth.getUser()   // 1. 先驗身分
  if (!user) return null
  const { data } = await supabase.from('profiles')           // 2. 再查資料
    .select('*').eq('id', user.id).single()
  return data
}
```

畫面 [src/app/page.tsx](../src/app/page.tsx) 只寫 `const profile = await getMyProfile()`，乾淨。✅

### 深入 & 面試講法（含「被誇大」的澄清）

**先講真話**：那份你看到的回答說「導入 DAL，未來要從 Supabase 遷到 Prisma 只要換 DAL 一層」——**這是話術，面試別這樣講**。原因：Supabase client 的查詢寫法（`.from().select().eq()`）和 Prisma（`prisma.stock.findMany()`）的形狀差非常多，真要換，DAL 內部幾乎重寫。DAL **不能**讓你「無痛遷移」。

**DAL 真正的價值（這才是該講的）**：
1. **集中化**：碰資料庫的邏輯只有一個地方，好維護。
2. **可測試**：DAL 是純函式，可以單獨寫單元測試。
3. **安全一致**：身分驗證統一在 DAL 做，不會這頁有檢查、那頁忘了檢查。
4. **只回傳該回傳的（DTO 概念）**：例如查使用者時，只 `select` id/name，不要把 `password_hash`、手機號整包丟出去。官方把這叫 **DTO（Data Transfer Object）**。

**兩個進階技巧（Next 16 官方文件就這樣教，講出來很加分）**：
- 用 React 的 `cache()` 把驗證函式包起來，**同一次請求內重複呼叫只會真的執行一次**。這正好解決「[middleware.ts](../src/middleware.ts) 做一次 `getUser()`、進頁面 DAL 又做一次」的重複往返：
  ```ts
  import { cache } from 'react'
  export const verifySession = cache(async () => { /* getUser()... */ })
  ```
- **安全檢查要貼著資料源做**（在 DAL 裡），不要只放在 layout 或最外層攔截器。因為 Server Actions、巢狀路由有多個入口，只在外層擋會有漏洞。

- **面試講法**：「我用 DAL 集中資料存取與授權邏輯，好處是可測試性與安全一致性——每個資料請求都保證跑過身分驗證。我也用 DTO 只回傳必要欄位避免過度暴露。我**不會**宣稱它能無痛換掉 Supabase，因為底層 query API 差異很大；DAL 的價值在維護性與測試，不在遷移。」

## 第 5 章：Migration as Code —— 用 SQL 檔管理資料庫

> **一句話**：資料庫的每一次結構變更（建表、改欄位、加政策）都寫成 `.sql` 檔、進 Git，而不是在後台網頁用滑鼠點。

### 從零開始：問題是什麼？

新手在 Supabase 後台網頁點一點就把表建好了。問題：
- 你換一台電腦、或同事加入，**沒有任何方法復現這個資料庫**——那些點擊沒被記錄下來。
- 「上禮拜誰把這個欄位改成可為空的？」沒有歷史，查不到。
- 正式環境和測試環境結構不一致，出事。

Migration（遷移檔）的概念：**把資料庫的演化史寫成一連串帶時間戳的 SQL 檔**，像 Git commit 一樣一筆筆累積。任何人 clone 專案，一行指令就能重建一模一樣的資料庫。

### 對應到你的專案

你已經在做了，這是強烈的加分項：

- [supabase/migrations/20260620144945_init_schema.sql](../supabase/migrations/20260620144945_init_schema.sql) ← 檔名前面那串就是時間戳，決定執行順序。
- [supabase/config.toml](../supabase/config.toml) ← Supabase CLI 的設定，代表你用 CLI 流程而非純手點。

常用指令（之後實作會用到）：
```bash
supabase migration new add_stocks_table   # 產生一個新的空白 migration 檔
supabase db push                           # 把本地 migration 推到雲端資料庫
supabase db reset                          # 砍掉本地 DB、從頭跑所有 migration（驗證可復現性）
```

### 深入 & 面試講法

- **黃金原則**：migration 一旦推上去、別人也跑過了，就**不要再改那個舊檔**——要改就新增一個 migration。（就像 git 不該改已 push 的歷史。）
- **面試講法**：「我的資料庫是 Database-as-Code：所有 schema、RLS 政策、trigger 都是 Git 裡的 SQL migration。任何人 clone 專案後 `supabase db reset` 就能在全新環境復現完全一致的資料庫，team 協作與 CI 都靠這個。」這句話能直接把你和「我都在後台點」的候選人區隔開。

## 第 6 章：Serverless 連線數爆炸 → Supavisor / 6543 / Transaction 模式

> **一句話**：Vercel 上每個請求都可能開一個新的臨時伺服器，各自想直連資料庫，瞬間就把資料庫的連線數塞爆。解法是中間加一個「連線池」共用連線。

### 從零開始：問題是什麼？

先懂兩個詞：
- **傳統伺服器**：一台長期開著的機器，開幾條到資料庫的連線，重複用。連線數穩定。
- **Serverless（Vercel 的模式）**：沒有長期開著的機器。**每個請求進來，才臨時生出一個小函式來處理，處理完就消失**。好處是自動擴展、不用管伺服器；壞處正是這章的主題。

問題：PostgreSQL 每開一條連線都吃不少記憶體，所以它有**連線數上限**（免費方案可能才 60 條）。Serverless 一旦同時來 200 個請求，就生出 200 個函式，每個都想直連資料庫 → `too many connections` 爆炸。

### 它怎麼運作：連線池（Connection Pooler）

解法是在「一堆臨時函式」和「資料庫」中間，放一個**連線池**——它自己跟資料庫維持少量固定連線，所有臨時函式都跟連線池借，用完還。就像「共享單車站」：不是每個人都自己買一台腳踏車，而是跟車站借、騎完還，少量的車服務大量的人。

Supabase 的連線池產品叫 **Supavisor**。關鍵就是**連接埠（port）選對**：

| 連法 | Port | 適合 | 你的情境 |
|---|---|---|---|
| 直連 (Direct) | **5432** | 長期開著的伺服器、跑 migration | ❌ 不適合 Serverless |
| 連線池 - **Transaction 模式** | **6543** | Serverless（Vercel） | ✅ **你要用這個** |
| 連線池 - Session 模式 | 5432(pooler) | 需要 session 狀態的特殊情況 | 少用 |

- **Transaction 模式**：連線**以一筆交易為單位**借還，交易一結束馬上還回去給別人用 → 複用率最高，最適合「來去一陣風」的 Serverless 函式。
- **Session 模式**：連線借了就綁住你整個 session 才還，複用率低。

你的 [supabase/config.toml:44-50](../supabase/config.toml) 本機設定裡 `pool_mode = "transaction"` 已經是對的方向。

> **好消息**：你目前用 `@supabase/supabase-js`（走 PostgREST，是 HTTP 介面，不是直接的 Postgres 長連線），這個連線爆炸問題沒那麼立即。但**只要你之後改用 Prisma / Drizzle 這種直連 Postgres 的工具，這題立刻變生死問題**——所以一定要懂。

### 面試講法

「因為 Vercel 是 Serverless，每個請求可能是獨立的執行環境，直連 Postgres（5432）會在併發升高時瞬間耗盡連線上限。我改用 Supabase 的 Supavisor 連線池、走 **6543 + transaction 模式**，讓連線以交易為單位最大化複用，避免 `too many connections`。」

## 第 7 章：Vendor Lock-in、冷啟動、流量計費

> **一句話**：用雲端服務很爽很快，但要清楚它們的三個代價：被綁死、第一次啟動慢、用量一大帳單陡升。面試官想聽的是「你知道代價，且有對策」。

### 7-1 冷啟動（Cold Start）

接續第 6 章：Serverless 函式平常是「睡著」的。第一個請求進來時，要先「叫醒」它（載入程式、初始化）——這段延遲叫**冷啟動**，可能多個幾百毫秒到一兩秒。之後一段時間內有請求進來就是「熱」的、很快；閒置久了又睡著。

- **對你的影響**：使用者**很久沒人訪問後**第一次打開股票頁，可能慢一下。
- **對策**：把高頻、不常變的頁面用「快取 / 預先產生靜態頁」處理（見下），請求根本不用叫醒函式去算。

### 7-2 執行時間限制（接你原始需求最痛的點）

Vercel 的 Serverless 函式有**最長執行時間限制**。你的專案如果想「使用者一按，就即時去爬證交所、算完一整批本益比再回傳」——很容易**超時**。

> **這正是第 10 章把『擷取資料』和『使用者讀資料』徹底分開的原因**：抓資料是背景排程慢慢做，使用者只讀已經算好的結果，秒回。

### 7-3 流量計費陡峭（Egress / Bandwidth）

免費額度很佛，但要知道計費**踩在哪**：
- **Egress（資料流出量）**：資料從 Supabase / Vercel「流出去」是要錢的。如果你每次都 `select('*')` 撈整張表給前端，流量會很可觀。
- **對策**：① 只 `select` 需要的欄位（呼應 DTO）；② 分頁；③ 快取高頻讀取，減少實際打資料庫的次數。

### 7-4 Vendor Lock-in（供應商綁定）

你越用某家的獨家功能（Supabase 的 RLS、Vercel 的獨家 API），將來要搬家越痛。
- **務實態度**：作品集階段，**綁定是合理取捨**——換來開發速度。面試別假裝你做了完全可移植的架構（會被戳破）。
- **該講的**：「我清楚我用了 Supabase/Vercel 的特定功能、也接受這個取捨換取開發效率；我用 DAL 把資料存取集中，至少把『未來要換』的修改範圍縮小到一層。但我不會宣稱無痛遷移。」

### 7-5 快取（把上面對策串起來）

Next.js 16 提供快取機制，讓「不常變的資料」不用每次都重算/重查：
- **Route Handler 預設不快取**（每次都即時跑），但 `GET` 可以選擇性開啟快取。
- Next 16 有 `use cache` 指示詞 + `cacheLife()` 可以指定「這份資料快取多久」。
- 「重新整理」快取則用 `revalidateTag` / `revalidatePath`。

> ⚠️ Next 16 的快取 API（`use cache`、Cache Components、`cacheLife`）和你印象中的舊版差異不小。真的要寫時，**先讀 `node_modules/next/dist/docs/01-app/01-getting-started/08-caching.md`**，不要照網路舊教學。

**你的情境很適合快取**：股價一天只更新一次（收盤後），所以「個股頁」「排行榜」可以快取數小時，使用者讀的是靜態結果，又快又省 egress 又躲掉冷啟動——一石三鳥。

### 面試講法

「我了解 Serverless 的三個代價：冷啟動、執行時間上限、egress 計費。所以我把重運算（抓證交所、算本益比）放到背景排程、與使用者請求解耦；讀取面用 Next.js 快取把一天才變一次的股價資料快取住，同時降低延遲與資料庫讀取成本。」

## 第 8 章：Observability（可觀測性）—— Sentry

> **一句話**：程式上線後會在「別人的機器上」出錯，你看不到 console。Observability 就是讓系統把「我哪裡痛、多痛」主動回報給你。

### 從零開始：問題是什麼？

本機開發時錯誤都印在你的終端機。但部署到 Vercel 後，程式在雲端跑，使用者遇到錯誤你**完全不知道**——除非他截圖罵你。Observability 解決的就是「上線後的眼睛」。

它通常包含三件事：
1. **Error tracking（錯誤追蹤）**：出錯時自動把錯誤、堆疊、發生在哪個使用者身上記下來、發警報。→ **Sentry** 是這類的代表。
2. **Logging（日誌）**：記錄系統做了什麼。
3. **Metrics / Tracing（指標／追蹤）**：例如「這個 Supabase 查詢花了多久」「哪個 API 變慢了」。

### 對應到你的專案（可加的亮點）

- 串 **Sentry**：Server Action 報錯、或證交所擷取失敗時自動記錄＋通知你。
- 你的擷取排程（第 10 章）**特別需要**這個——因為它在背景跑，沒人盯著。「昨天的股價沒抓到」你得**主動被通知**，而不是使用者發現資料是舊的才知道。
- 加 **Vercel Analytics** 看流量。

### 面試講法

「我串了 Sentry 做錯誤追蹤，尤其是背景的資料擷取排程——它無人看守，所以我讓它在失敗時主動告警，並記錄每次執行的成功/失敗與筆數。這是大多數學生作品不會做、但正式系統一定要有的可觀測性。」

> 這章是「99% 新手作品沒有」的差異化點，投入小、講起來很專業，**性價比很高**。

## 第 9 章：測試 —— Playwright E2E + RLS 測試

> **一句話**：手動點點看不叫測試。自動化測試是「寫程式去驗證你的程式」，讓你改東西時有信心不會弄壞別處。

### 從零開始：測試的層次

由小到大，業界常分三層（「測試金字塔」）：

| 層次 | 測什麼 | 你的專案例子 | 工具 |
|---|---|---|---|
| **單元測試 (Unit)** | 單一函式的邏輯 | 「本益比計算函式輸入 X 回傳 Y」 | Vitest / Jest |
| **整合測試 (Integration)** | 幾個部件接起來 | 「DAL 查詢 + RLS 政策是否真的擋住越權」 | Vitest + 測試用 DB |
| **端對端測試 (E2E)** | 模擬真人用瀏覽器 | 「打開首頁 → 點登入 → 看到 dashboard」 | **Playwright** |

### 兩個你該做的

**1. Playwright E2E**：它會**真的開一個瀏覽器**，照你寫的腳本點按鈕、填表單、檢查畫面。

```ts
import { test, expect } from '@playwright/test'

test('未登入者造訪 dashboard 會被導到 login', async ({ page }) => {
  await page.goto('/dashboard')
  await expect(page).toHaveURL(/.*login/)   // 驗證你 middleware 的保護真的有效
})
```

**2. RLS 測試**：用 SQL/腳本驗證「我假裝成 user A，是否真的讀不到 user B 的私密資料」。這直接證明你第 3 章的安全防線**真的有效**，不只是寫了政策放著。

### 面試講法

「我用 Playwright 寫關鍵流程的 E2E（登入、受保護路由導向），並針對 RLS 寫測試模擬越權存取、確認資料庫層真的擋得住。測試讓我重構時有信心，也讓 RLS 這道防線是**被驗證過**的，而不是寫了就假設它有效。」

> 對作品集，**先求有**：把「登入流程」和「未登入被擋」這兩條 E2E 寫出來，價值就很高，不用一開始追求高覆蓋率。

## 第 10 章：【解方】證交所 API 資料擷取架構

這是你專案**最有工程含金量**的部分，也是面試最能展現你深度的地方。我先點出現況問題，再給完整架構。

### 10-1 先處理那個問題：為什麼不要 `證交所 → Google Sheets → Supabase`？

把 Google Sheets 夾在資料管線中間，是面試官第一個會質疑的點。它的問題：
- **沒有 schema/型別**：欄位可被手滑改壞，數字變字串。
- **沒有交易（transaction）**：寫到一半失敗，資料半殘。
- **有 API 配額與延遲**：Google Sheets API 不是為高頻資料管線設計的。
- **無法承載時間序列**：你要存「每天每檔」的歷史，試算表很快就爆。

**結論**：除非你有「需要非技術人員手動編輯/校正」的明確理由（那它是個 human-in-the-loop 覆寫層，要這樣講），否則**拿掉它**，直接 `證交所 API → 擷取程式 → Supabase`。

### 10-2 核心心法：把「寫入（擷取）」和「讀取（使用者）」徹底分開

這是整個解方的靈魂，也直接化解第 7 章的 Serverless 超時問題：

```
【寫入流／離線】每天收盤後跑一次，慢沒關係：
   證交所 API ──▶ 擷取程式（驗證+轉換+冪等寫入）──▶ Supabase

【讀取流／線上】使用者來訪，只讀資料庫，秒回：
   使用者 ──▶ Next.js（Server Component + 快取）──▶ 讀 Supabase ──▶ 回畫面
```

使用者**永遠不會**等你去爬證交所——他們讀的是已經算好、存好的資料。

### 10-3 「擷取程式」放哪跑？（決策表）

| 方案 | 怎麼運作 | 優點 | 缺點 | 建議 |
|---|---|---|---|---|
| **GitHub Actions 排程** | 在 GitHub 用 cron 定時跑一支 Node/Python 腳本，抓完用 service_role 金鑰寫 Supabase | 免費、**無 Serverless 超時問題**（可跑數十分鐘）、本身就在 Git 裡（呼應你的技術棧）、log 看得到 | 與網站程式分開 | ⭐ **作品集首選** |
| **Supabase Edge Function + 排程** | 用 Supabase 內建排程（pg_cron / Scheduled Functions）觸發 Edge Function | 離資料庫近、全在 Supabase 生態 | Deno 環境、也有執行時間限制 | 次選 |
| **Vercel Cron → Route Handler** | Vercel 定時打你的 `app/api/cron/route.ts` | 和網站同一個 repo、最少額外設定 | **受 Vercel 函式超時限制**（資料量大會爆） | 資料量小才用 |

**我的建議**：用 **GitHub Actions**。理由：它沒有超時問題（最痛的點直接消失）、免費、且「排程設定也是 Git 裡的程式碼」非常呼應你「Database-as-Code」的專業敘事。

### 10-4 資料怎麼存？（時間序列建模 —— 有料的 DB 設計）

不要像 `profiles` 那樣一列搞定。股價是**時間序列**：每天、每一檔，一筆。拆成兩張表：

```sql
-- 公司主檔（很少變）
create table public.stocks (
  id           text primary key,        -- 股票代號，如 '2330'
  name         text not null,           -- '台積電'
  market       text,                    -- 'TWSE' / 'TPEX'
  created_at   timestamptz default now()
);

-- 每日報價（時間序列，量會很大）
create table public.daily_quotes (
  stock_id     text not null references public.stocks(id),
  trade_date   date not null,
  close_price  numeric(10,2),
  pe_ratio     numeric(10,2),           -- 本益比
  volume       bigint,
  created_at   timestamptz default now(),
  primary key (stock_id, trade_date)    -- ★ 複合主鍵 = 同一檔同一天只會有一筆
);

-- 查單一檔的走勢會用到，加索引加速
create index idx_quotes_stock_date on public.daily_quotes (stock_id, trade_date desc);

-- RLS：公開可讀、前端不可寫（只有後端 service_role 能寫）
alter table public.stocks enable row level security;
alter table public.daily_quotes enable row level security;
create policy "public read stocks" on public.stocks for select using (true);
create policy "public read quotes" on public.daily_quotes for select using (true);
```

> 那個 `primary key (stock_id, trade_date)` 是整個設計的關鍵——它讓「重複抓同一天」不會產生重複資料（接下來的「冪等」就靠它）。

### 10-5 擷取程式的四個工程要點（這些是面試深度）

**① 冪等（Idempotency）—— 重跑不會壞**
排程可能因為失敗而重跑、或你手動補抓。所以「抓同一天兩次」結果必須一樣。用 `upsert`（有就更新、沒有就新增），靠上面的複合主鍵：

```ts
// 抓回來、轉換後，一次 upsert 進去
const { error } = await supabase
  .from('daily_quotes')
  .upsert(rows, { onConflict: 'stock_id,trade_date' })  // ★ 衝突就覆蓋，不報錯、不重複
```

**② 三段式：抓取 → 驗證/轉換 → 寫入**
別把「抓」和「寫」混在一起。先抓 raw、驗證（用 Zod 之類確認證交所回傳格式沒變、數字真的是數字）、轉成你的 schema，最後才寫。任何一段失敗都能清楚定位。

**③ 重試 + 禮貌（對外部 API）**
證交所 API 會偶爾失敗或限流。要做：
- **重試**：失敗等幾秒再試（指數退避 exponential backoff），試幾次還不行才放棄。
- **禮貌**：分批抓、每批之間 sleep 一下，別狂打人家 API。

**④ 可觀測（接第 8 章）**
每次排程記錄：抓了幾檔、成功/失敗、花多久。失敗就用 Sentry 告警——因為它在背景跑，沒人盯。

### 10-6 密鑰放哪？（接第 1、3 章）

- 擷取程式寫資料庫要用 **`SUPABASE_SERVICE_ROLE_KEY`**（萬能金鑰，**繞過 RLS**）。
- 它**只能**待在 Server 世界 / GitHub Actions 的 Secrets 裡，**絕對不可**出現在前端、不可加 `NEXT_PUBLIC_` 前綴、不可進 Git。
- 這就是為什麼「前端不能寫、只有後端能寫」（10-4 的 RLS 設計）成立：前端拿的是 anon key 被 RLS 管著，後端排程拿 service_role key 才寫得進去。

### 10-7 一張圖總結這個解方

```
                         GitHub Actions（cron：每天 14:30 收盤後）
                                      │
                                      ▼
              ┌──────────────────────────────────────────────┐
              │  擷取程式                                       │
              │  1. 抓 證交所 API（重試 + 禮貌限流）              │
              │  2. Zod 驗證 + 轉換成 schema                    │
              │  3. upsert 進 daily_quotes（冪等，靠複合主鍵）    │
              │  4. 記錄筆數/耗時；失敗 → Sentry 告警            │
              │     用 SUPABASE_SERVICE_ROLE_KEY（只在這裡）     │
              └──────────────────────────────────────────────┘
                                      │ 寫入
                                      ▼
                               Supabase (Postgres)
                          stocks / daily_quotes（RLS：公開讀、禁前端寫）
                                      │ 讀取
                                      ▼
              Next.js（Server Component + 快取數小時）──▶ 使用者（秒回）
```

### 面試講法

「我把資料管線拆成寫入流與讀取流：擷取用 GitHub Actions 排程在收盤後執行，避開 Serverless 的執行時間限制；寫入用複合主鍵 + upsert 做到冪等，重跑或補抓都不會產生重複；對證交所 API 做重試與限流；service_role 金鑰只存在於排程環境，前端由 RLS 限制為唯讀。使用者端只讀已算好的資料並加上快取，所以又快又省成本。原本的 Google Sheets 中介層我移除了，因為它沒有 schema、交易與型別保證，不適合放在正式資料管線裡。」

## 附錄 A：名詞快速對照

| 名詞 | 一句話白話 |
|---|---|
| Server Component | 在伺服器上算好畫面，預設值，能碰密鑰與資料庫 |
| Client Component | 標 `'use client'`，在瀏覽器跑，負責互動 |
| JWT | 使用者的身分證明 token，`header.payload.signature` |
| `getUser()` | 向 Auth 伺服器查證身分（可信） |
| `getSession()` | 只本地讀 cookie（Server 端不可信） |
| RLS | 長在資料庫每一列上的權限鎖，最後防線 |
| DAL | 集中所有資料庫存取的那層程式 |
| DTO | 只回傳必要欄位，不整包丟出 |
| Migration | 帶時間戳的 SQL 檔，資料庫的演化史 |
| Connection Pooler / Supavisor | 連線共享站，解決 Serverless 連線爆炸 |
| Transaction 模式 / 6543 | 以交易為單位借還連線，Serverless 適用 |
| Cold Start | Serverless 函式被叫醒的初次延遲 |
| Egress | 資料流出量，計費項目 |
| Idempotency（冪等） | 同樣操作做幾次結果都一樣 |
| Observability | 上線後系統主動回報健康/錯誤的能力 |
