## 1. 先建立心智模型：GitHub Actions 是什麼

**一句話**：GitHub 免費提供一台「用完即丟的雲端電腦」，你可以設定「在某個時間點，自動開一台這種電腦，把你的專案 clone 下來、跑幾個指令」。

從零開始理解四個名詞（由大到小）：

| 名詞 | 是什麼 | 你的例子 |
|---|---|---|
| **Workflow（工作流）** | 一個 `.yml` 檔，描述「什麼時候、做什麼」 | `.github/workflows/ingest.yml` |
| **Trigger（觸發器）** | 什麼事件會啟動這個 workflow | 每天 09:00 UTC（排程）、或手動按按鈕 |
| **Job（工作）** | 在一台全新的雲端電腦上執行的一整組步驟 | `ingest` 這個 job |
| **Step（步驟）** | job 裡的一行指令或一個現成動作 | checkout → 裝 Node → `npm ci` → `npm run ingest:ci` |

**關鍵心法**：這台雲端電腦（GitHub 叫它 **runner**）是**全新、乾淨、用完即丟**的。它不知道你電腦上的任何東西——沒有你的 `node_modules`、沒有你的 `.env.local`、沒有你裝過的工具。所以 workflow 必須**從零把環境重建起來**：clone 程式碼 → 裝 Node → 裝套件 → 才能跑。這解釋了為什麼 workflow 裡有 checkout、setup-node、`npm ci` 這些步驟——在你自己電腦上這些早就有了，但 runner 什麼都沒有。

這台電腦「用完即丟、什麼都不知道」的特性，也正好呼應[開發核心觀念教學.md 第 6 章](./開發核心觀念教學.md)講的 Serverless 概念——runner 就是一種 serverless 的執行環境。

## 2. 一個關鍵前置修正：CI 沒有 .env.local

原本的 `package.json` 腳本是：

```json
"ingest": "node --env-file=.env.local --import tsx scripts/ingest/run.ts"
```

`--env-file=.env.local` 會**強制讀取那個檔案**。但 `.env.local` 被 `.gitignore` 排除了（放祕密的地方，不進 git）——所以 runner 上**根本沒有這個檔案**，直接執行會報錯。

**解法**：新增一條 CI 專用腳本，不指定 `--env-file`：

```json
"ingest:ci": "node --import tsx scripts/ingest/run.ts"
```

差別只在於**金鑰從哪來**：

- 本機 `npm run ingest`：從 `.env.local` **檔案**讀。
- CI `npm run ingest:ci`：從**環境變數**讀（由 GitHub Secrets 在執行時注入，見第 4 節）。

兩者最終都是讓 `scripts/ingest/supabase-admin.ts` 裡的 `process.env.SUPABASE_SERVICE_ROLE_KEY` 拿到值，只是來源不同。程式本身完全不用改。

> 我們有在本機模擬 CI 驗證過這條路徑：用 `set -a; source .env.local; set +a` 把金鑰匯出成環境變數（而非透過檔案），再跑 `npm run ingest:ci`，結果正常寫入 2380 筆。

## 3. workflow 檔案逐行拆解

檔案位置**固定**要放在 `.github/workflows/` 底下（GitHub 只認這個路徑）：[.github/workflows/ingest.yml](../.github/workflows/ingest.yml)

```yaml
name: Ingest stock data          # 在 GitHub Actions 分頁上顯示的名稱

on:                               # ── 觸發器 ──
  schedule:
    - cron: '0 9 * * 1-5'         # 每個工作日 09:00 UTC 自動跑
  workflow_dispatch:              # 也允許在網頁上手動按鈕觸發（測試用）

permissions:
  contents: read                  # 最小權限：只讀程式碼，不給寫回 repo 的權限

jobs:
  ingest:                         # job 的代號
    runs-on: ubuntu-latest        # 用哪種 runner（最新版 Ubuntu Linux）
    timeout-minutes: 10           # 超過 10 分鐘就強制中止，避免卡住的 job 一直計費/佔用
    steps:
      - uses: actions/checkout@v4 # 步驟1：把你的 repo clone 到 runner 上
      - uses: actions/setup-node@v4  # 步驟2：在 runner 上安裝 Node.js
        with:
          node-version: 22        #   用 Node 22（LTS 穩定版）
          cache: npm              #   快取 npm 套件，加速下次執行
      - run: npm ci               # 步驟3：依 package-lock.json 精準安裝套件
      - run: npm run ingest:ci    # 步驟4：跑擷取（CI 版腳本）
        env:                      #   ↓ 把 GitHub Secrets 注入成環境變數
          NEXT_PUBLIC_SUPABASE_URL: ${{ secrets.NEXT_PUBLIC_SUPABASE_URL }}
          SUPABASE_SERVICE_ROLE_KEY: ${{ secrets.SUPABASE_SERVICE_ROLE_KEY }}
```

幾個值得記住的重點：

- **`uses:` vs `run:`**：`uses:` 是套用別人寫好的現成動作（像 `actions/checkout`），`run:` 是直接跑 shell 指令。
- **`@v4`** 是版本號：釘住主要版本，避免哪天上游改壞影響你。
- **`npm ci` 而非 `npm install`**：`ci` 會嚴格照 `package-lock.json` 安裝、且會先清空 `node_modules`，保證每次環境一模一樣（可重現性，呼應教學文件反覆強調的原則）。
- **`env:` 區塊裡的 `${{ secrets.XXX }}`**：這是把「金庫裡的祕密」注入成環境變數的語法。金鑰**不會**寫在這個檔案裡（這個檔會進 git），只寫「去金庫拿名為 XXX 的祕密」。金庫怎麼設定見下一節。
- **`workflow_dispatch`**：加了這行，你才能在網頁上手動觸發測試，否則只能痴痴等排程時間到。

## 4. 你必須手動做的兩件事

程式碼準備好了，但有兩件事**只能你自己在 GitHub 網頁上做**，我無法代勞：

### ① 把兩個金鑰加進 GitHub Secrets（金庫）

到你的 repo 網頁：**Settings → Secrets and variables → Actions → New repository secret**

新增兩個 secret（名稱要**完全一致**，大小寫也是）：

| Name | Value |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | 你 `.env.local` 裡那個 `https://xxx.supabase.co` |
| `SUPABASE_SERVICE_ROLE_KEY` | 你 `.env.local` 裡的 service_role 金鑰 |

> **為什麼要用 Secrets 而不是直接寫進 yml？** 因為 yml 會進 git、會被推上 GitHub，任何看得到 repo 的人都會看到。`SUPABASE_SERVICE_ROLE_KEY` 是繞過所有 RLS 的最高權限金鑰，**外洩等於資料庫門戶大開**。Secrets 是加密儲存的，連你自己之後都看不到原文，且在 log 裡會被自動遮蔽成 `***`。

### ② 把 workflow 檔案 commit 並 push 到預設分支（main）

**GitHub Actions 的排程只會從 repo 的預設分支（`main`）執行**。所以這個 `.yml` 檔一定要進到 GitHub 上的 `main` 分支才會生效：

```bash
git add .github/workflows/ingest.yml package.json docs/
git commit -m "chore: 加入 GitHub Actions 每日擷取排程"
git push origin main
```

推上去之後，到 repo 的 **Actions** 分頁，就會看到 "Ingest stock data" 這個 workflow。

## 5. 如何測試（不必等到明天）

因為我們在 workflow 加了 `workflow_dispatch`，可以立刻手動觸發，不用等到 09:00 UTC：

1. 到 repo 網頁的 **Actions** 分頁。
2. 左側點 **Ingest stock data**。
3. 右側點 **Run workflow** 按鈕 → 再按綠色的 **Run workflow**。
4. 幾秒後會出現一筆執行紀錄，點進去看即時 log。

**成功的樣子**：綠色勾勾，log 最後出現 `[ingest] 完成，共寫入 2380 筆...`。

**失敗的樣子**：紅色叉叉。最常見原因與對照：

| log 出現 | 原因 | 解法 |
|---|---|---|
| `缺少 NEXT_PUBLIC_SUPABASE_URL 或 SUPABASE_SERVICE_ROLE_KEY` | Secret 沒設定，或名稱拼錯 | 回第 4 節①檢查 secret 名稱是否完全一致 |
| `new row violates row-level security policy` | Secret 值貼錯，貼成了 anon key 而非 service_role | 重新到 Supabase Dashboard → Settings → API 複製 **service_role** 那把 |
| 卡在 `npm ci` 失敗 | `package-lock.json` 沒推上去 | 確認 `git push` 有包含 lock file |

## 6. cron 時間怎麼算（UTC vs 台灣）

`cron: '0 9 * * 1-5'` 這五個欄位的意思：

```
┌───── 分鐘 (0)
│ ┌─── 小時 (9)         ← UTC 時間！
│ │ ┌─ 日 (* = 每天)
│ │ │ ┌─ 月 (* = 每月)
│ │ │ │ ┌ 星期 (1-5 = 週一到週五)
0 9 * * 1-5
```

**最容易搞錯的點：GitHub 的 cron 用 UTC，不是台灣時間。** 台灣是 UTC+8，所以：

```
09:00 UTC + 8 小時 = 17:00 台灣時間
```

台灣股市 13:30 收盤，日成交資料通常下午稍晚才公布完整，所以設 17:00（台灣）給足緩衝。**如果你想改時間**，先想好台灣時間，再減 8 小時換成 UTC 填進去。例如想要台灣時間晚上 8 點跑：`20 - 8 = 12`，寫成 `0 12 * * 1-5`。

> 小工具：[crontab.guru](https://crontab.guru) 可以貼上 cron 字串、即時看它代表什麼時間。

## 7. 已知限制與陷阱

這些是 GitHub Actions 排程的真實特性，面試被問到能講出來會加分：

1. **排程只從預設分支（main）跑**：改了 workflow 一定要 push 到 `main` 才生效（見第 4 節②）。
2. **排程時間不保證精準**：GitHub 在整點負載高時，排程可能延遲數分鐘到十幾分鐘才啟動。對「每天抓一次」不影響，但別拿它做「秒級精準」的事。
3. **repo 閒置 60 天，排程會自動停用**：如果你 60 天沒有任何 commit，GitHub 會停掉排程並寄信通知，需要手動重新啟用。作品集平常沒在動的話要注意。
4. **台灣國定假日仍會觸發**：`1-5` 只排除週末，不知道台灣的國定假日。假日當天市場沒開，API 可能回傳空資料或前一交易日的資料：
   - 若回傳**前一交易日**資料 → 因為我們是冪等 upsert，重寫一次同樣的資料無害。
   - 若回傳**空**資料 → `run.ts` 會以結束碼 1 結束，那次 run 顯示紅色失敗（一個「假警報」）。目前選擇接受這個小噪音；若要根治，需引入台灣交易日曆判斷，或把「空資料」改判定為正常結束。

## 8. 常見調整

| 想做的事 | 怎麼改 |
|---|---|
| **改執行時間** | 改 `cron` 的 UTC 時間（第 6 節） |
| **改成一天跑兩次** | 加第二行 cron，例如收盤後與晚上各一次：<br>`- cron: '0 9 * * 1-5'`<br>`- cron: '0 13 * * 1-5'` |
| **新增更多資料源要用的金鑰** | 在 GitHub Secrets 加新 secret，並在 workflow 的 `env:` 區塊多加一行對應 |
| **失敗時想收到通知** | GitHub 預設會寄 email 給 workflow 檔的最後修改者；進階可在最後加一個 step 串 Slack/Discord webhook 或 Sentry |
| **暫時停用排程** | Actions 分頁 → 選該 workflow → 右上 `···` → Disable workflow |
